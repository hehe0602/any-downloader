## 1. 快速上手

### 1.1 环境

| 项 | 要求 | 说明 |
|---|---|---|
| Python | 3.10+ | 本机在 3.13 验证；代码用 `from __future__ import annotations`，部分模块用 `str \| None` 写注解 |
| 操作系统 | Windows 10/11 | 会话（WebView2）、托盘、单实例互斥体都依赖 Windows；非 Windows 只能跑 CLI 与引擎 |
| WebView2 运行时 | Win11 自带 | Win10 装 Edge 即有；缺了 GUI 起不来 |
| `curl.exe` | 可选 | `transport_probe` 用它做 Schannel 传输栈探测；缺失时该列为 `ERR`，不影响主流程 |

依赖只有三个（`requirements.txt`）：

```
httpx[http2]>=0.27
pywebview>=5.1
curl_cffi>=0.7        # Chrome TLS 指纹后端，缺失时自动退化为 httpx
```

### 1.2 三条常用命令

```powershell
# 装依赖（清华镜像，Windows 上 pip 直连常超时）
py -3.13 -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

# 跑 GUI
py -3.13 main.py

# 跑 CLI（无界面，脚本/回归用）
py -3.13 main.py --cli "http://127.0.0.1:8000/f.bin" -o "D:\tmp\f.bin" -t 8 -c 4
```

**前端不需要任何构建步骤**：`web/index.html` 用 `<script src="vendor/vue.global.prod.js">` 直接引入
Vue 3 的 global 构建，改完 `app.js` / `style.css` / `index.html` 重启窗口即生效（没有 webpack / vite）。

## 2. 总体架构

### 2.1 分层

```
        ┌─────────────────────────────────────────────┐
        │  web/（Vue3 单页，无构建）                    │
        │  app.js  ← appBridge(event)  事件             │
        │          → pywebview.api.*()  请求            │
        └───────────────┬─────────────▲───────────────┘
                        │             │ evaluate_js("window.appBridge(...)")
              ┌─────────▼─────────────┴─────────┐
              │  app/api.py  JsApi              │  同步解包 Future → 纯 dict/list
              └─────────┬─────────────▲─────────┘
                        │ run_coroutine_threadsafe
              ┌─────────▼─────────────┴─────────┐
              │  app/manager.py DownloadManager │  独占一个事件循环线程
              │  任务表 / 事件增量 / 诊断 / 退出  │
              └─────────┬─────────────▲─────────┘
                        │             │ on_event 回调（同一线程）
              ┌─────────▼─────────────┴─────────┐
              │  app/downloader.py DownloadTask │  asyncio 协程 + 64 Worker
              └───────┬──────────┬──────────────┘
                      │          │
        ┌─────────────▼──┐   ┌───▼────────────────┐
        │ transports.py  │   │ checkpoint.py      │
        │ httpx/curl_cffi│   │ .ckpt.json 原子写   │
        └────────────────┘   └────────────────────┘

        app/session.py（WebView2，UI 线程 + 独立读取线程）
        app/tray.py（WinForms NotifyIcon，UI 线程 + 短线程回调）
```

### 2.2 线程模型（最容易踩坑的地方）

| 线程 / 名称 | 谁创建 | 跑什么 | 硬约束 |
|---|---|---|---|
| 主线程（UI） | Python 启动进程 | `webview.start()`、WinForms 消息循环 | 禁止在此跑阻塞下载；所有 WebView2 操作最终落在这里 |
| `download-loop` | `DownloadManager.__init__` | 所有引擎协程、诊断、`shutdown` 协调 | 只有它能 `await` 引擎；外部通过 `_submit()` 投递协程 |
| `session-cookies`（临时） | `SessionManager._read_cookies` | 阻塞式 `window.get_cookies()` | 必须 `join(_COOKIE_TIMEOUT)`；超时抛 `TimeoutError` |
| `tray-tooltip` | `main.run_gui` | 每 3 秒刷新托盘悬停提示 | 只读 `manager.tasks`，不碰引擎 |
| `tray-restore` / `tray-quit` | `TrayIcon` 菜单回调 | 调 `window.show/restore`、退出流程 | **必须**是短线程：菜单回调本身在 UI 线程，直接调 pywebview 会 `Invoke` 重入 |

跨线程规则（写新代码时逐条遵守）：

1. 从 UI/托盘线程调引擎 → 一律走 `manager.xxx()`（内部 `run_coroutine_threadsafe`）+ `.result()`；
2. 从 `download-loop` 向前端推消息 → `manager.notify()` / `_push()`，pywebview 会自己 marshal 到 UI 线程；
3. 会话操作可能阻塞（建窗、等 `loaded`、读 Cookie）→ 必须用 `asyncio.to_thread(...)` 包一层再进引擎，
   否则整个下载循环会被卡住（`_add_download` / `_resume_task` 就是这么做的）；
4. 托盘图标/菜单的创建与销毁统一经 `TrayIcon._invoke()`（`form.Invoke`），
   窗体已销毁时用 `dispose_direct()` 而不是 `dispose()`。

### 2.3 一次「新建下载」的完整链路

直链流程：

```
浏览器点「开始下载」
  → app.js  submitForm() → pywebview.api.add_download(opts)
  → api.py   JsApi.add_download() → manager.add_download(opts).result()
  → manager  _submit() → 在 download-loop 里执行 _add_download(opts)
      1. 校验 url / save_dir，构造 DownloadConfig
      2. 没有 cookie 且 auto_credentials → await asyncio.to_thread(_apply_credentials)
           → credential_provider(url) → SessionManager.capture(url) → 注入 cookie/UA/Referer
      3. DownloadTask(tid, cfg, on_event=self._on_task_event) 入表
      4. _start_runner()：按 cfg.transport 建 httpx 或 curl_cffi 客户端，
         起 asyncio 任务跑 task.run()
      5. 返回 task.snapshot(full=True)
  → api.py   Future.result() 拿到 dict，pywebview 序列化回 JS
  → app.js   upsertFull(t) 插入卡片
（随后每秒 2 次的 task_update 事件通过 evaluate_js 推过来）
```

分享链接流程（粘贴后先经 `resolve_link`，见 4.7）：

```
粘贴链接 → app.js scheduleResolve()（500ms 防抖）→ api.resolve_link({url, passcode})
  → classify()：直链 / 已接入分享 / 未接入分享(unsupported)
  → 分享：取会话凭据 → 未登录抛 LoginRequiredError（api 层自动开窗，前端切登录面板）
         → parser.parse_share() 拉根目录 → 返回 ShareResult payload
  → 点文件夹：api.list_share_dir()（面包屑返回，目录缓存）
  → 勾选文件（可跨目录多选）→ submitForm() 带 share={site, share_url, pwd_id, stoken, files, selected}
  → _add_download() 分享分支：复查登录态 → 重建 ShareResult → parser.issue_direct_urls()
         批量换成 CDN 签名直链 → 每个文件各走一遍上面直链流程的 2~5，返回 {created, count}
```

## 3. 核心引擎 `app/downloader.py`

### 3.1 `DownloadConfig` 字段

`app/config.py`，dataclass，全部有默认值：

| 字段 | 类型 / 默认 | 作用 |
|---|---|---|
| `url` | str（必填） | 直链 |
| `save_dir` | str（必填） | 保存目录 |
| `filename` | `""` | 空则由 `Content-Disposition` / URL 推导 |
| `concurrency` | `64` | Worker 数 |
| `chunk_size` | `4 * MB` | 目标分块；经 `normalized_chunk_size()` 夹到 2~5MB |
| `min_chunk_size` / `max_chunk_size` | `2MB` / `5MB` | 夹取上下限 |
| `user_agent` | Chrome 130 | 会被会话的真实 UA 覆盖 |
| `referer` | `""` | 非空则优先于站点默认 |
| `send_default_referer` | `True` | 关掉后「不发送 Referer」成为可选项（诊断修正会用到） |
| `cookie` | `""` | 会话注入或手工粘贴 |
| `extra_headers` | `{}` | cURL 导入的其余头，最后覆盖同名默认头 |
| `use_client_hints` | `True` | 用真实 UA 时自动置 False，避免指纹自相矛盾 |
| `use_http2` | `False` | **默认关闭**：多连接才能各自吃满单连接限速 |
| `verify_tls` | `True` | 对应 `curl -k` |
| `transport` | `"httpx"` | 或 `"curl_cffi"`（Chrome TLS 指纹） |
| `connect_timeout` / `read_timeout` | `15` / `60` 秒 | 传给 `httpx.Timeout(read, connect=)` |
| `max_retries` | `12` | 单分块重试次数 |
| `cookie_refresher` | `None` | 回调 `() -> str`；403/412 时重取会话 Cookie |

`build_headers(cfg, with_cookie=True, with_referer=True)` 是**唯一**的请求头构造函数，
探测、诊断、分块下载全部走它——保证「诊断出来的结论」和「真实下载行为」一致。

### 3.2 状态机

```python
class TaskStatus(str, Enum):
    QUEUED, CONNECTING, DOWNLOADING, PAUSED, COMPLETED, CANCELED, ERROR
```

```
            add_download
                 │
                 ▼
              QUEUED ──run()──► CONNECTING ──probe 成功──► DOWNLOADING
                 │                   │                       │
                 │                   │ probe 致命错误         ├─ 全部块完成 ─► COMPLETED（_finalize）
                 │                   ▼                       ├─ 用户暂停 ───► PAUSED
                 │                 ERROR ◄── _FatalError ────┤   （仍有块未完成）
                 │                   ▲                       ├─ 用户停止 ───► CANCELED
                 │                   └── 未捕获异常 ──────────┘
                 │
      PAUSED/CANCELED/ERROR ──resume_task()/重试──► CONNECTING（reset_for_restart 后重新 run）
```

| 常量 | 值 | 用途 |
|---|---|---|
| `ACTIVE_STATUSES` | queued / connecting / downloading | 判断「是否需要先暂停再操作」、托盘统计 |
| `TERMINAL_STATUSES` | completed / canceled / error | CLI 轮询退出条件 |

注意：

- `run()` 结束时若「既没被取消、也没有致命错误、但块没下完」→ 状态置 `PAUSED`（不是 error）；
- 状态迁移只发生在 `download-loop` 线程，UI 侧只读快照，不要在前端推导状态。

### 3.3 分块与调度

```
probe 拿到 total_size
   → cs = clamp(chunk_size, 2MB, 5MB)
   → adaptive = total_size // concurrency，若 > 0 则 cs = min(cs, max(256KB, adaptive))
        （小文件自动切小块，保证每条连接都有活干）
   → chunks = [ (start, min(total, start+cs)-1), ... ]        闭区间
   → queue = 未完成块的索引（asyncio.Queue）
   → N 个 Worker 循环：limiter.acquire() → queue.get_nowait() → 下载 → limiter.release()
```

- **每个 Worker 自己开文件句柄**（`open(output, "r+b")`，懒打开，退出时关闭），
  用 `fh.seek(start)` 按偏移直写，互不干扰；
- `queue.get_nowait()` 取空 → Worker 退出（不是忙等）；
- 文件先 `truncate(total_size)` 预分配，避免边下边扩；
- 不支持 Range（探测返回 200）→ `segmented=False`，退化为**单连接整文件**下载（`_download_whole`）。

### 3.4 `run()` 主流程

```python
async def run(self):
    self.reset_for_restart()
    try:
        self.status = CONNECTING; self._emit()
        await self._probe()             # GET Range: bytes=0-1，识别 size / Range 支持 / 文件名
        os.makedirs(save_dir, exist_ok=True)
        await self._build_and_restore() # 切块 + 读检查点 + 预分配文件
        self._queue = asyncio.Queue()    # 只放未完成的块索引
        self._limiter = DynamicLimiter(concurrency)
        self.status = DOWNLOADING; self._emit()
        self._monitor_task = create_task(self._monitor())
        await asyncio.gather(*[create_task(self._worker(w)) for w in range(concurrency)])
        self._monitor_task.cancel(); self._limiter.shutdown()
        # 判定：fatal → ERROR｜canceled → CANCELED｜块全完成 → _finalize()｜其他 → PAUSED
    except _FatalError as e:  self.status = ERROR；self.error = str(e)
    except Exception as e:    self.status = ERROR；self.error = "类型: 消息"
    finally:
        self.active.clear(); self._chunk_progress.clear(); self._speed_samples.clear()
        self.speed = 0.0; self.eta = None   # ← 必须在 _done_event.set() 之前
        self._done_event.set()
        self._emit()
```

`_probe()` 的细节：**不发 HEAD**（网盘 CDN 常按 UA/方法拦 HEAD），而是 `GET` + `Range: bytes=0-1`：

| 探测结果 | 处理 |
|---|---|
| 206 | 记录 `total_size`（从 `Content-Range: bytes 0-1/总数` 取）、`Content-Disposition` 文件名 |
| 200 | 记录 `Content-Length`，标记不支持 Range |
| 429 | `Retry-After` / 指数退避后重试（最多 3 次） |
| 403 / 412 | 先尝试 `_fallback_transport()`，再 `_refresh_cookie()`，最后抛 `_FatalError(_auth_hint(code))` |
| 其他 | 抛 `_FatalError` |

### 3.5 重试与退避矩阵

单个分块（`_download_range` / `_download_whole`）遇到的状态码：

| 状态码 | 动作（按顺序尝试） | 用尽后 |
|---|---|---|
| 206 / 200 | 正常读流写入 | — |
| 429 | `_limiter.rate_hit(_retry_delay())`：全局限流暂停 + 并发减半 → 继续下一次 attempt | `_fail(_auth_hint(429))` |
| 403 / 412 | ① `_fallback_transport()`（httpx → curl_cffi，只切一次）② `_refresh_cookie()`（30s 节流）③ `_backoff()` | `_fail(_auth_hint(403/412))` |
| 416 | 直接 `_fail(_auth_hint(416))`（二分重试同区间无意义） | 立即终止 |
| 分块模式收到 200 | `_fail("服务器忽略了 Range 请求…")` | 立即终止 |
| 其他 4xx/5xx | 4xx 立即 `_fail`；5xx 走 `_backoff` 重试 | `_fail` |

退避公式（都带抖动，避免 64 个 Worker 同时重试形成尖峰）：

```python
_retry_delay(resp, attempt)  # 尊重 Retry-After；否则 min(30, 0.5*2**attempt) + U(0, 0.5)
_backoff(attempt)            # min(20, 0.3*2**attempt) + U(0, 0.4)
```

`DynamicLimiter`（403/429 自愈）：

- `current` 从 `target` 起；命中限流时 `current = max(min_limit, current * 0.75)`
  —— 原来是一刀砍半，256 并发下一瞬间掉到 4，恢复又要 15 秒一档慢慢爬，
  长任务上表现成「爆发一下、瘫很久」；
- 命中瞬间置 `_paused=True` 让所有 Worker 停手，但**全局暂停上限 6 秒**
  （`_RATE_PAUSE_CAP`）：完整的 `Retry-After` 由命中的那个 Worker **自己补睡**
  `max(0, delay - _RATE_PAUSE_CAP)`（`_download_range` / `_download_whole` 的 429 分支）
  —— 既不能把几百个在途分块一起按住几十秒，也不能 6 秒就打回去招来更重的限速；
- `rate_limited` 是**带时效的 property**（冷却 `_RATE_COOLDOWN = 90s`）：它会影响并发
  策略，做成永久粘住的标志位会让一次抖动把整段下载钉在低并发上；
- `release()` 用 `cond.notify(1)` 而不是 `notify_all()`：走掉一个只空出一个名额，
  池子固定 256 个协程时 `notify_all` 会让每个分块完成都白唤醒 255 个；
- 之后每 15 秒 `current = min(target, current + max(2, target//8))` 阶梯恢复；
- 多个 Worker 同时命中只处理一次（`cond` 保护），其余等待；
- `set_target(n)` 支持**热改并发**（界面上「改并发」按钮）：调小立即生效（在途分块
  跑完为止，不会中途丢数据），调大在没有被限速过时立即生效；`min_limit` 会跟着下调，
  用户把并发设成 2 也听他的；任务不在运行态时不动限流器（旧对象上起 ramp 是空转）。

**并发自适应**（`adaptive_concurrency`，默认开）：引擎的分块数是按并发数切出来的
（`_desired_span`），所以「一上来 target 路全开」在按 URL/IP 聚合限速的 CDN 上很容易
直接触发限速（实测夸克某 6GB 直链：256 路只有 3MB/s，而同一张网卡别的文件能到 12MB/s）。
控制器改成**定向探测**而不是无脑拉满：

- 档位 `8 → 16 → 32 … → target`（`_setup_adapt`），每档观察 `_ADAPT_PROBE_WINDOW = 6` 秒；
- 每档量一次实际吞吐（`_wire_bytes` 增量 / 时间），与**上一档**比：
  提升不足 `_ADAPT_MIN_GAIN = 12%` 就认为到了拐点，收敛到历史最佳档位（`_settle_adapt`）；
- 吃到 429/403 时**先在原档再观察一个窗口**（`_adapt_backoffs`），仍然被限速才收敛 ——
  一次抖动不足以断言"就是并发太高"；
- `_settle_adapt` 定的是**实测档位** `_adapt_best_level`，不是 `limiter.current`
  （后者可能刚被 429 临时砍过，如 8 → 6）：拿它当结论会把一次抖动固化成永久设置，
  还会让 `target` 一起变小、连阶梯恢复都失效；
- 结果写进 `adapt_note`（如「并发自适应：定在 8 路（实测约 1.4 MB/s）」）随快照给界面；
  没测满窗口时不谎报速度（`_adapt_best_bytes == 0` 就不写速率）；
- `_adapt_tick` 在 `_monitor` 里被 try 包住：自适应只是锦上添花，它出错绝不能把
  监控协程带走（监控一死，周期落盘、测速、ETA、事件推送就全停了）；
- 关掉 `adaptive_concurrency` 就回到「一上来 target 路全开」的老行为（CLI 默认关闭，
  这样 `-t 256` 立即生效；GUI 默认开启）；
- 用户手动改并发 → `_adapt_done = True`，控制器不再插手。

### 3.6 传输栈自动兜底

`_fallback_transport()`：

- 只在 `cfg.transport == "httpx"` 时生效，且只切一次（切完 `cfg.transport = "curl_cffi"`）；
- 关掉旧客户端、新建 `CurlCffiClient`，**保留用户的 IPv4 偏好与并发上限**
  （`prefer_ipv4=`、`max_clients=curl_pool_size(...)`）——漏传等于悄悄回到被限速的
  IPv6 路径、或被 curl 默认的 10 个句柄卡住；
- 设置 `transport_note` 推给前端展示（勾了 IPv4 时文案里会注明）；
- `curl_cffi` 未安装 / 导入失败 → 返回 `False`，退化为原有的 Cookie 刷新 + 退避。

它解决的是「Cookie 和请求头都对，但服务端按 TLS/JA3 指纹拦 Python 客户端」这一类 412。

### 3.7 中途 Cookie 轮换

`_refresh_cookie()`：

- 依赖 `cfg.cookie_refresher`（由 manager 在注入凭据时挂上），`None` 就直接返回 False；
- 距上次刷新不足 30 秒 → 直接返回 False（避免 64 个 Worker 一起打登录会话）；
- 取到**不同的** Cookie 才算成功（返回 True → 立即重试当前块）；
- 回调抛异常被吞掉，不影响下载。

### 3.8 测速与 ETA（近 60 秒滑动平均）

常量：`_SPEED_WINDOW = 60.0`、`_SPEED_TICK = 0.5`。

- `_wire_bytes`：真正从网卡收到的字节（含重试重复的部分），只增不减；
- `_speed_samples`：`deque[(monotonic, wire_bytes)]`，`maxlen=400`，每 0.5 秒一个点；
- `_roll_speed(now)`：
  1. 丢掉窗口外的采样，但**保留一个越界锚点**，让跨度始终 ≥ 60 秒；
  2. `speed = (wire_now - anchor_bytes) / (now - anchor_ts)`；
  3. 窗口未满时等价于「自开始以来的平均」，所以一开始就有读数；
  4. 没有新数据时窗口会把速度摊回 0。
- **暂停/停止/完成/出错必须归零**，这里有三重保证：
  1. `request_pause()` / `request_cancel()` 第一件事就是 `_freeze_speed()`（立刻归零 + `_emit()`）；
  2. `run()` 的 `finally` 再归零一次，且在 `_done_event.set()` **之前**（这样 `pause_task()` 拿到的快照也是 0）；
  3. `reset_for_restart()` 清空采样窗口，暂停的空档不会被算进恢复后的平均。
- ETA = `(total - done) / speed`，`speed <= 1` 或已下完时置 `None`。

> 改这里之前先想清楚：`speed` 是**给用户看的平滑值**，不是容量规划数据。

### 3.9 事件回调与 `snapshot()`

```python

```

`_emit()` 在每个关键点调用（探测完、每 0.5 秒、状态变化、结束），由 manager 转成
`task_update` 推给前端。回调异常被吞掉——**事件推送失败不能影响下载**。

`snapshot(full=False)` 字段（前端契约，改字段要同步 `web/app.js` 与本文档）：

## 4. 下载管理器 `app/manager.py`

### 4.1 线程与 Future 约定

```python
def _submit(self, coro) -> concurrent.futures.Future:
    return asyncio.run_coroutine_threadsafe(coro, self._loop)
```

- 所有公开方法（`add_download` / `pause_task` / `resume_task` / `cancel_task` / `remove_task` /
  `list_tasks` / `probe_link` / `probe_task` / `transport_probe` / `apply_probe_fix` /
  `apply_transport`）都返回 `Future`；
- **同步解包只在 `app/api.py` 做**（pywebview 6.x 不会自动解包 Future，直接返回会
  `Object of type Future is not JSON serializable`）；
- 协程里抛的异常会被 `Future.result()` 原样重抛，前端拿到的是 rejected Promise。

### 4.2 任务生命周期 API

| 方法 | 行为 |
|---|---|
| `add_download(opts)` | 校验 → 建 cfg → 注入凭据 → 建任务 → 起 runner |
| `pause_task(tid)` | 活动状态 → `request_pause()` + `wait_done(120)`；返回归零后的快照 |
| `resume_task(tid)` | 已终态直接返回；否则**重新读一次会话凭据** → `reset_for_restart()` → 重新起 runner |
| `cancel_task(tid)` | 活动状态 → `request_cancel()` + `wait_done`；否则直接置 `CANCELED` |
| `remove_task(tid, delete_files)` | 先取消并等收尾，再可选删 `output_path` / `.ckpt.json` / `.ckpt.tmp`，最后推 `task_removed` |
| `list_tasks()` | 全量快照（`full=True`），并把 `_sent` 重置为当前 `completed` |
| `snapshot_now(tid)` | 同步读当前快照（CLI 轮询用） |

`opts` 的键（前端 `add_download` 传的字段）：

```
url, save_dir, filename, concurrency, chunk_size(MB), user_agent, referer, cookie,
extra_headers{}, use_http2, verify_tls, use_client_hints, transport,
auto_credentials(默认 True), _cookie_refresher(内部用),
# 分享任务专用（resolve_link 成功后由前端回传，见 4.7）
share={site, share_url, share_title, pwd_id, stoken, referer, files[], selected[]}
```

`resolve_link` 的 `opts` 键：`url`、`passcode`（面板手动输入的提取码，链接本身没带时用）。

### 4.3 凭据注入链路

```
manager.credential_provider  ← JsApi.__init__ 注入（self.session 是那个 SessionManager 实例）
                                lambda url: self.session.capture(url)
manager._apply_credentials(cfg, url)
  ├─ cookie 为空 → 直接失败（记 _cred_note，前端弹 toast）
  ├─ 有 cookie → cfg.cookie = cookie
  ├─ 有 user_agent → cfg.user_agent = it; cfg.use_client_hints = False
  ├─ cfg.referer 为空 → 用会话给的站点 Referer
  └─ cfg.cookie_refresher = lambda: provider(url)["cookie"]   ← 供下载途中 403/412 用
```

两个入口直接调用它：新建任务、`resume_task()`（点重试/继续时**重新**读一次会话）。
这两处都包在 `asyncio.to_thread` 里（会话可能建窗、等页面加载，会阻塞几百毫秒到十几秒，
不能占住下载事件循环）。下载途中的 403/412 走 `cfg.cookie_refresher`（3.7 节），
由引擎在分块重试里调用。

> 分享任务的 `cookie_refresher` 绑定回**分享域名**而不是 CDN host：CDN host 上按
> `GetCookiesAsync(uri)` 读不到父域登录 Cookie，刷新时必须用 `pan.quark.cn` 那一侧取。

### 4.4 诊断

| 方法 | 做什么 | 返回 |
|---|---|---|
| `probe_link(opts)` | 用**表单值**建临时 cfg，跑 Cookie × Referer 组合 | `{host, cookie_present, referer, combos[], best, verdict}` |
| `probe_task(tid)` | 用**任务自己的 cfg** 跑同样组合 | 同上 |
| `transport_probe(tid)` | `build_headers(task.cfg)` + 4 种传输栈各打一次 | `{curl_backend, transports[]}` |
| `apply_probe_fix(tid, use_referer)` | 改 `send_default_referer` / 清 `referer` → 重试 | 任务快照 |
| `apply_transport(tid, kind)` | 改 `cfg.transport` → 重试 | 任务快照 |
| `task_url(tid)` | 取直链（给 `browser_probe` 用） | str |

组合的取舍（`_probe_combos`）：没有 Cookie 时只跑 `referer` 和 `plain` 两组，不做等价重复。

`_probe_verdict()` 把状态码翻译成人话并指明**下一步动作**（直接下载 / 去掉 Referer / 去登录 /
直链过期），前端直接展示这段文案，不在 JS 里重复判断。

### 4.5 事件推送协议

manager → 前端，全部经 `window.appBridge(event)`：

```jsonc
// 任务增量（每秒 2 次 + 状态变化时）
{"type": "task_update", "task": { /* snapshot() 全部字段 */, "completed_delta": [12, 13] }}

// 任务被移除
{"type": "task_removed", "id": "a1b2c3d4"}

// 独立 Toast（不挂任务）
{"type": "toast", "message": "已重新读取会话凭据，正在重试", "level": "success"}
```

实现要点：

- `_push()` 用 `evaluate_js` 注入 **JS 对象字面量**（`window.appBridge({...})`），
  不是 `JSON.parse`；序列化时 `ensure_ascii=False`，并把 `U+2028/2029` 转义（JS 里是换行符，
  不转义会造成语法错误）；
- 增量靠 `_sent[tid]`（已推送的块索引集合）算 diff；`list_tasks` 会把 `_sent` 重置，
  避免重连后重复推一大坨；
- 窗口不存在或已销毁时 `_push` 静默失败（下载不因为界面没了而中断——托盘场景必需）。

### 4.6 优雅退出

```
shutdown(wait=10)
  → _submit(_stop_all)：对每个活动任务 request_pause()（会先归零速度）→ 等 gather（超时 8s）
  → loop.call_soon_threadsafe(loop.stop)
  → thread.join(5)
  → 线程收尾：run_until_complete(_aclose_all()) → 取消剩余协程 → loop.close()
```

信号入口 `install_signal_handlers()`（**必须在主线程调用**）：`SIGINT`/`SIGTERM`，
Windows 上另加 `SIGBREAK` 与 `SetConsoleCtrlHandler` 处理 `CTRL_CLOSE / LOGOFF / SHUTDOWN`
（这两类事件系统只给几秒，所以用独立线程 `shutdown(wait=6)` 快速落盘）。

### 4.7 分享链接解析（插件框架）

参考 LinkSwift「每个网盘一套模块」的分层：前端只认通用 `share` 结果结构，网盘差异全部
封装在解析器插件里。

**分类（`app/parsers/registry.py`）**：`classify(url)` 返回三类——

| kind | 条件 | 行为 |
|---|---|---|
| `direct` | 未命中任何分享正则，也不是已知网盘域名上的 `/s/`、`/share/` 路径 | 直链原样下载 |
| `share` | 命中某已接入解析器的 `share_patterns` | 走该解析器 |
| `unsupported_share` | 已知网盘域名（`sites.py`）但路径像分享页、且注册表没有解析器 | 抛 `UnsupportedShareLinkError`，前端提示「接口已预留，待适配」 |

**Manager 三个相关协程**：

- `resolve_link(opts)`：直链原样返回；分享链接先 `asyncio.to_thread` 取会话凭据，
  `logged_in` 为假抛 `LoginRequiredError`；否则构造 `ParseContext` 调
  `parser.parse_share(url, ctx)`，把 `ShareResult.to_dict()` 加上 `kind:"share"`、
  `site_name` 回给前端。面板手动输入的提取码会拼到 URL 查询串 `?pwd=` 上再分类与解析。
- `list_share_dir(opts)`：前端点文件夹 / 面包屑时调用。用回传的 `pwd_id` / `stoken`
  重建 `ShareResult`，调 `parser.list_dir(result, dir_fid, ctx)` 翻页拉取该目录条目，
  返回形状与 `resolve_link` 的 share 结果一致（同样先过登录态校验）。
- `_add_download()` 的 `share` 分支：按 `share.site` / `share_url` 找回解析器 → 复查会话
  （有 Cookie 就放行，见 6.4）
  → 从回传的 `files`（前端只回传勾选的条目）里按 `selected` 重建 `ShareFile`（文件夹直接
  报错）→ `issue_direct_urls()` 批量拿到 CDN 签名直链 / 文件名 / Referer，
  **每个文件独立创建一个下载任务**，返回 `{created:[快照...], count}`。
  会话 Cookie / UA / Referer 带进 `DownloadConfig`（**Cookie 用解析器写回的 `ctx.cookie`**，
  它可能已被刷新过 `__puus`）；`use_client_hints` 在有真实 UA 时关闭；
  `cookie_refresher` 绑定回分享域名（见 4.3 末尾说明）。
  仅选中一个文件时，表单手填的文件名才覆盖解析结果。

**异常契约**（`app/parsers/base.py`，`api.py` 翻译成前端面板状态）：

**解析器接口**（`ShareParser` 抽象基类）：`site_key`（对应 `sites.py` 键）、`share_patterns`、
`match(url)`、`extract_passcode(url)`、`async parse_share(url, ctx) -> ShareResult`、

**23018 到底是什么（踩过两次歧路，别再踩）**

`file/download` 对分享文件返回 `23018 download file size limit` 时，它只有一个含义：
**服务端没把这轮请求当成已登录的客户端**。两件互相独立的事都会触发它：

- **请求没带上有效会话**（Cookie 没读出来 / 票据过期）。服务端原文常带 `[guest]`，
  「游客可下载大小受限」就是自白。真实事故：`capture()` 读 Cookie 的实现有 bug
  （改了 `BrowserForm.url` 而不是 `EdgeChrome.url`，见 6.3），请求以游客身份发出；
- **UA 是浏览器 UA**（2026-11-07 真机 A/B，新发现）。同一组 Cookie、同一个 248MB
  分享文件：`User-Agent` 用会话里的 Edge UA → `23018`；换成 LinkSwift 那套
  `quark-cloud-drive/2.5.x` 的 PC 客户端 UA → `code=0` 并返回直链。
  网页端 UA 自带访客级下载大小上限，跟账号是不是会员无关。
  **这是「浏览器里 LinkSwift 能签、下载器签不出」的根因。**

所以现在的实现是：`_client()` 固定用 `API_UA`（PC 客户端 UA），签发前再用
`__pus` 刷新短时效票据 `__puus`（见 `app/cookie_refresh.py` 与 6.4）。
`23018` 按「没被认成已登录」处理，抛 `LoginRequiredError` 引导重新扫码。

排查顺序：先确认这轮请求真的带上了 `__pus/__puus` 且 `__puus` **没过期**
（用会话 Cookie 打 `member` 看 `code=0`；拿签出的直链做一次 `Range` 请求看
206 还是 412/403），再怀疑账号/站点规则。

**不转存（2026-11-07 起）**

解析器只做「列目录 → 签直链」：不调 `sharepage/save`、不轮询 `task`、不往用户
网盘里写任何东西。用户已确认「不需要转存，浏览器里的 LinkSwift 也不转存」。
历史版本曾把 23018 误判成「大文件必须转存」并加了兜底；那条路径既非必要，
账号容量不足时还会直接 `32003 capacity limit` 失败，已整体删除
（`_save_then_sign / _ensure_save_dir / _wait_save_task / _raise_save_error /
_capacity_text` 与相关常量）。

**调 API 用哪个 UA**

`_client()` **固定用 `API_UA`**（`QuarkPC/6.9.7.761 … quark-cloud-drive/2.5.40`），
不要用 `ctx.user_agent`。会话里的真实 Edge UA 只用于 CDN 下载（CDN 不挑 UA，
只认 Cookie 里的有效票据）；`ctx.user_agent` 仍保留在 `ParseContext` 里给迅雷等
其他网盘用。

> **真机验证状态（2026-11-07）**：公开分享 + 已登录会话下，248MB 文件的
> `token → detail → file/download` 全部 `code=0`，签出的直链 `Range` 请求 206；
> 同一组 Cookie 换成 Edge UA 则 23018。过期 `__puus` 会让 CDN 返回 412 / 403，
> 刷新票据后恢复。字段再变时只改 `app/parsers/quark.py` 的映射，主流程不动。

**百度网盘（2026-11-09 重写，`app/parsers/baidu.py`）**

之前百度模块用的是 `GET /share/list` + HTML 正则解析 `shareid/uk`，真机上**根本列不出目录**：
`/share/list` 对真实分享统一返回 `errno=2`「链接出错了」（老接口已废）。现在的流程：

1. **链接口径**：`/s/1<token>` 的 `token` **含开头 1**，`/share/wxlist` 要完整 token；
   `/share/verify` 等旧接口要 `surl = token[1:]`。两个口径都封装在
   `_extract_token / _token_to_surl`，不要再手写切片。
2. **列目录**：`POST /share/wxlist?channel=weixin&version=2.2.2&clienttype=25&web=1`，
   表单 `shorturl=<token>&dir=<绝对路径>&root=1|0&pwd=<提取码>&page&num=1000&order=time`。
   响应 `data.{list,seckey,shareid,uk,title}`；`seckey` 是 URL-safe Base64
   （`- ~ _`），`_decode_seckey()` 转成标准 Base64 才能塞进 `extra.sekey`。
   提取码也由它校验：`errno=-130` + `errtype="mispwd-9"` = 缺/错提取码；**不要**
   再依赖 `/share/verify`（无提取码分享也会回 -12，无法区分）。
3. **文件夹 key**：`ShareFile.key` 对文件夹必须是**绝对路径**（wxlist 的 `dir` 收路径，
   不收 `fs_id`），文件仍用 `fs_id`。否则点文件夹会 `mis_2 不存在此目录`。
4. **签发**（必须登录，匿名一律 `9019 need verify`）：
   - `GET /api/gettemplatevariable?fields=["bdstoken","username","loginstate"]`
     取 `bdstoken`；`loginstate != 1` 抛 `LoginRequiredError`；
   - `GET /share/tplconfig?fields=sign,timestamp&surl=<token>` 取 5 分钟有效的
     `sign/timestamp`（失败时用 `shareid&uk` 口径再试一次）；
   - `POST /api/sharedownload?sign&timestamp&bdstoken`，表单
     `encrypt=0&extra={"sekey":<seckey>}&fid_list=[fs_id]&primaryid=<shareid>
     &uk=<uk>&product=share`，响应 `list[0].dlink`；
     参数类错误（`2/113`）会依次换 `clienttype=0+netdisk;+无 type` →
     `clienttype=12+网页 UA+type=nolimit` → `clienttype=12+netdisk;+type=nolimit`
     三套口径再试（`_DOWNLOAD_VARIANTS`）；
   - `extra` 里的 sekey 用标准 Base64（`+ / =`），不要再 URL 编码一次；
   - **提取码分享在签发前会再列一次根目录**：wxlist 成功会下发 `BDCLND` Cookie，
     `sharedownload` 除 `extra.sekey` 外也看它；同时顺手刷新可能过期的 seckey。
5. **下载 UA**：`dlink` 必须用 `pan.baidu.com`，浏览器 UA 下 >50MB 会 403。
   `ResolvedFile.user_agent` 专门承载这个值，Manager 建任务 / 续传重签都会用它；
   同时 `use_client_hints=False`，避免 UA 与客户端提示自相矛盾。
6. **302 预解析**：签发后 `Range: 0-1` 跟一次 302 拿最终 CDN 地址，避免 64 路并发
   各跳一次；解析失败退回原 dlink。
7. **错误码**：`9019/-6/31045/31064/31066` → 登录；`-20` → 风控验证码；
   `112` → 刷新 sign 重试一次；`118` → 重新 `wxlist` 取 seckey 重试一次；
   `-9` 文件不存在；`-1` 违规；`2/113` 参数类错误；`116` 分享不存在；
   `121` 一次选太多文件。**不转存**，不往用户网盘写任何东西。
8. **stoken**：格式 `shareid|uk|seckey`（seckey 是 Base64，不含 `|`）；旧任务只有
   `shareid|uk` 也能解，签发时会重新列一次根目录补 seckey。

> **真机验证状态（2026-11-09）**：无登录会话下已实测 `/share/wxlist` 能列根目录、
> 进入子文件夹、拿到 3 个文件的 `fs_id/size/seckey`；缺码/错码/取消/失效的错误码映射
> 均已对上；`/share/tplconfig` 能取到 sign/timestamp。**登录态下的 `/api/sharedownload`
> 因本机 WebView2 没有 BDUSS，尚未真机复验**，链路按 LinkSwift 2026 版与
> baiduwp-php 的实现对齐；`tests/test_baidu.py` 用 MockTransport 覆盖了 54 项
> 请求字段 / 错误映射 / 112·118 重试。拿到真实登录会话后，先跑 `resolve_link` →
> 勾选文件夹内文件 → 开始下载，确认 `sharedownload` 返回 `list[0].dlink` 且
> `Range: 0-1` 为 206 即可。

### 5.2 前端约定

- **不要用构建工具**：Vue 是 `web/vendor/vue.global.prod.js`（global 构建），
  新增依赖请手写到 `vendor/`，保持「断网可用」；
- **必须等 `pywebviewready`**：`mounted()` 里先判断 `window.pywebview.api`，没有就监听
  `pywebviewready`。早期 bug 就是 `mounted()` 早于 API 注入，导致误报「请通过 main.py 启动应用」
  并跳过 `loadAll()`；
- 事件入口是全局函数 `window.appBridge(ev)` → `vm.onBackendEvent(ev)`；
  调试时还可以用 `window.__vm`（`app.js` 末尾有意暴露的实例）；
- **任务对象在 JS 里是「两个集合」**：
  - `tasks[id]` 是 Vue 响应式对象，收到 `task_update` 时 `Object.assign(existing, t)`；
  - `tasks[id]._done` 是本地维护的 `Set`（已完成块），用 `completed_delta` 增量累加。
    原因是非 full 快照的 `completed` 字段是 `null`，直接覆盖会丢掉已完成块。
  **因此不要在模板里依赖 `t.completed`**，用 `cellClass()` 读 `_done`；
- 时间/体积格式化只在 JS 做（`formatBytes` / `formatEta`）；后端只给原始数字；
- **设置回填**：`mounted()` 的启动链是 `bootSettings() → loadAll() → loadSessionSites() → refreshSession(true)`；
  `bootSettings()` 先 `get_settings()` 回填目录 / 并发 / 分块，目录为空再取 `get_default_dir()`；
  浏览目录与提交成功后 `_persistSettings()` 调 `save_settings()` 落盘，重启自动记住；
- **分享面板状态机**：`this.share` 单一对象承载五种状态，`watch:"form.url"` 同时触发会话刷新
  与 500ms 防抖 `scheduleResolve()`；`applyResolveResult(res)` 把后端 `kind` 映射到面板；
  - 目录浏览：`crumbs`（面包屑，根目录 fid `"0"`）、`currentDir`、`dirCache`（fid→files，
    来回切换不重复请求）；点文件夹走 `enterDir → loadDir → list_share_dir`，
    点面包屑走 `goCrumb`；非 share 返回（need_login / error）交回状态机；
  - 多选：`selected`（key 数组）与 `selectedMap`（key→文件，跨目录累积），
    `toggleFile` / `toggleSelectAll`（全选当前目录），勾选数与总体积实时统计；
  - `submitForm()` 在 `need_login` / `passcode_*` 状态直接拦截，`share` 状态要求至少勾选一个文件，
    只回传勾选的文件，再组装 `share` 载荷；后端回 `need_login` 时把面板切到登录引导（见 4.7）；
    分享返回 `created` 时逐个 upsert 快照；
- 速度与剩余时间的显示规则集中在 `speedText()` / `etaText()`：

  | 状态 | 速度 | 剩余时间 |
  |---|---|---|
  | `downloading` / `connecting` | `formatBytes(speed) + "/s"` | `formatEta(eta)` |
  | 其他（paused / completed / canceled / error / queued） | `—` | `—` |

## 6. 内置会话 `app/session.py` + `app/sites.py`

### 6.1 为什么需要

网盘 CDN 直链在服务端校验登录态；纯 HTTP 请求即使把 UA / Referer / Sec-Fetch-* / HTTP2
组合试遍也只会拿到 412（README 有实测记录）。缺的是浏览器会话 Cookie，
而新版 Edge 的 Cookie 是 App-Bound 加密（`v20`），本地解不开、也不该去解开。

因此：**用 WebView2（Edge 内核）自己持有会话，需要凭据时向它要。**

### 6.2 三类窗口

| 窗口 | 可见 | 用途 | 创建点 |
|---|---|---|---|
| 登录窗 `_windows[site]` | 是 | 用户扫码登录 | `open(site)` |
| 读取窗 `_readers[site]` | 否（`hidden=True`） | 仅提供「该站点的文档上下文」，让 CookieManager 能读到持久化的 Cookie | `_reader(site)`，重启后自动建 |
| 探测窗 `_probes[host]` | 否 | 给 `browser_probe` 提供同源 origin | `_probe_window(host, scheme)` |

三类窗口都在 `_lock` 保护下按 key 复用；`clear(site)` 只删**该站点域名下**的 Cookie
再 `destroy()`。

> **别用 `window.clear_cookies()`**：pywebview 底层是 `DeleteAllCookies()`，会把所有网盘的
> 登录态一起清掉（实测踩过：清夸克把百度也清了）。`_delete_site_cookies()` 走
> CookieManager：UI 线程里 `GetCookiesAsync` + 按域名 `DeleteCookie`，调用方用信号量等结果；
> 拿不到后端（非 Windows / interop 变化）就一条都不删，绝不退回全局清空。

### 6.3 按任意 URL 取 Cookie（核心技巧）

pywebview 的 `window.get_cookies()` 只查「当前页面 URL」（内部 `GetCookiesAsync(self.url)`）。
`_read_raw_cookies(window, urls)` 的做法：把查询用的 URL 临时换掉，读完立刻还原。

> **坑（踩过）**：pywebview 6 的 winforms 后端是两层结构 ——
> `BrowserView.instances[uid]` 拿到的是 **BrowserForm**，它的 `url` 只在建窗时赋一次值；
> `get_cookies()` 真正使用的是 **EdgeChrome**（`BrowserForm.browser`）上的 `url`（导航时更新）。
> 只改外层等于什么都没改，读到的永远是「窗口当前页面」的 Cookie，
> 站点被重定向到风控页/运营商页时就一个登录 Cookie 都读不到。

```python
def _cookie_backends(window):            # [EdgeChrome, BrowserForm]，能改到的都改
    form = BrowserView.instances.get(window.uid)
    return [b for b in (getattr(form, "browser", None), form) if hasattr(b, "url")]

# 一轮读多个候选 URL 再取并集（单一路径会被 domain/path 规则漏掉东西）
queries = [target_url, SITES[site]["login_url"], *(f"https://{d}/" for d in domains)]
for target in queries:
    for backend in backends:
        backend.url = target            # 只改记录，不发请求、页面不动
    raw += window.get_cookies()
```

- 整个过程在独立线程里执行并 `join(_COOKIE_TIMEOUT=12)`：读 Cookie 可能等 UI 线程/页面加载；
- 后端对象取不到（非 Windows 或 pywebview 内部改了）→ 退化为「按当前页面 URL」取，保证可用；
- **必须自己按 RFC 6265 过滤**（`filter_for_url`），拿到的是「这几个 URL 能看到的 Cookie 并集」，
  不过滤就会把无关站点的 Cookie 发给 CDN：

  | 规则 | 判定 |
  |---|---|
  | domain | `host == domain` 或 `host.endswith("." + domain)`；空 domain 视为 host-only 放行 |
  | path | `url_path.startswith(cookie_path)` |
  | secure | Cookie 带 `Secure` 时 URL 必须是 https |

- `cookie_header(items)` 拼 `Cookie:` 头，同名 Cookie 保留 **path 更具体** 的那条。

### 6.4 登录态判定

`logged_in` 看的是**标志 Cookie 名**（`SITES[site]["login_cookies"]`，例：夸克的
`__pus/__puus`），判定时用**没按 URL 过滤的**并集 —— path/domain 规则有可能把标志 Cookie
挡在门外，用过滤后的结果判登录会把已登录误判成未登录。

> 别把 `__kp/__kps/__ktd/tfstk/isg/xlly_s` 这类风控指纹 Cookie 算作标志：未登录也会下发。
> 夸克扫码登录后一定会下发 `__pus`（HttpOnly）与 `__puus`。

**它只是启发式判断，不能当闸门。** `manager._needs_login()` 的规则是：

```
logged_in 为真            → 放行
有 cookie（过滤后的 Cookie 头非空）→ 放行，让服务端裁决
两者都空（一个 Cookie 都没有）→ 才要求登录
```

服务端说没登录（夸克 `31001 require login [guest]`）或要提取码时，解析器会抛
`LoginRequiredError` / `PasscodeRequiredError`，`api` 层照样自动开窗并切到登录引导面板。

> `23018`（分享文件签发）也按登录问题处理：它的含义是「服务端没把这轮请求认成
> 已登录客户端」（票据过期 / 浏览器 UA），现在抛 `LoginRequiredError`，`api` 层会
> 自动开登录窗。判定与 UA 的坑见 4.7。

早期版本直接用 `logged_in` 硬拦 `resolve_link / list_share_dir / add_download`，
结果读超时或父域 Cookie 缺失就把「已经登录」的用户挡在门外（README 修复记录有实测）。

### 6.5 `browser_probe`（浏览器栈基准）

用途：判定「浏览器能下、第三方客户端不行」= 传输层被拦。

1. 把隐藏探测窗导航到 `{scheme}://{host}/robots.txt`，拿到该 host 的**文档 origin**
   （同源 fetch 不受 CORS 限制，也不会触发文件下载）；
2. `evaluate_js` 注入 `fetch(url, {headers: {Range: bytes=0-1}, credentials: "include"})`，
   结果写进 `window.__bp`；
3. 每 0.25 秒 `evaluate_js("JSON.stringify(window.__bp)")` 轮询（**不能**在
   `evaluate_js` 里 await Promise），超时 20 秒；
4. 返回 `{name: "WebView2(Chromium)", status, bytes, content_range}`。

### 6.6 加一个网盘站点

只改 `app/sites.py` 的 `SITES`：

```python
"quark": {
    "name": "夸克网盘",              # 界面显示名
    "login_url": "https://pan.quark.cn/",   # 登录窗地址，也是判登录态时的目标 URL
    "referer": "https://pan.quark.cn/",     # 默认防盗链 Referer
    "domains": ("quark.cn",),               # 域名归属（含子域），也是查 Cookie 的候选 URL
```

若还要支持「分享链接 → 直链」解析，除了站点表条目，再按 10.2 在 `app/parsers/` 补对应模块。

## 7. 传输层 `transports.py` / `transport_probe.py`

### 7.1 引擎用到的 httpx 子集

引擎只依赖下面这几个东西，`CurlCffiClient` 就是照着实现的**鸭子类型**：

```python
await client.aclose()
async with client.stream("GET", url, headers=..., follow_redirects=True, timeout=...) as r:
    r.status_code           # int
    r.headers               # 支持 .get("content-range") 的映射
    await r.aread()         # 读完并返回 bytes（对应 httpx.Response.aread）
    async for piece in r.aiter_bytes(131072): ...
```

坑（都已踩过）：

- `curl_cffi.requests.AsyncSession` **不接受** `connect_timeout`，只有一个总 `timeout`；
- `_CurlResponse` 必须自己实现 `aread()`，否则探测路径 `await r.aread()` 会 `AttributeError`；
- 超时传参要转换：`_timeout_seconds()` 把 `httpx.Timeout` / float / None 统一成秒数。

### 7.2 四种传输栈探测

`probe_transports(url, headers)` 同步执行（manager 用 `asyncio.to_thread` 包了一层），
全部只请求 `Range: bytes=0-1`，不会真的下载：

| 名称（返回 `name`） | 实现 | 说明 |
|---|---|---|
| `httpx(当前)` | `httpx.Client` | 引擎默认栈，Python/OpenSSL |
| `httpx(Chrome TLS)` | 同上 + `_chrome_ssl_context()` | 把 TLS1.2 密码套件顺序换成 Chrome 的（JA3 的 ciphers 段对上，extensions 仍不同） |
| `curl.exe(Schannel)` | `curl -sS -o NUL -w "%{http_code}" -r 0-1 --http1.1` | 系统原生 TLS 栈；`curl_path()` 会找 PATH / System32 / Sysnative |
| `curl_cffi(Chrome)` | `curl_cffi.requests.get(impersonate="chrome")` | 复现 Chrome TLS/HTTP2 指纹 |

浏览器栈（第 5 种）在 `session.browser_probe`，因为需要 GUI 会话。

前端 `trName()` 负责把 `name` 映射成中文短名（`"WebView2(Chromium)" → "浏览器栈"`），
**新增传输栈时两边都要加**，否则卡片上显示原始英文名。

## 8. 托盘与单实例 `app/tray.py` + `main.py`

### 8.1 为什么不用第三方库

pywebview 在 Windows 上已经把 pythonnet + WinForms 载入进程，直接用
`System.Windows.Forms.NotifyIcon` 即可，零新增依赖（`clr.AddReference("System.Windows.Forms")`）。

### 8.2 线程模型

- `NotifyIcon` 必须活在**有消息循环的 UI 线程**：所有创建/更新/销毁都经
  `_invoke(fn)` → `form.Invoke(Action(fn))`；
- 菜单点击回调本身在 UI 线程，回调里只起短线程（`tray-restore` / `tray-quit`），
  再调 `window.show()/restore()`（内部又会 `Invoke`）——直接在回调里调会重入卡死；
- `dispose()`：从任意线程移除图标（正常退出用）；
  `dispose_direct()`：**已经在 UI 线程**（例如 `FormClosed`）时用，避免往已销毁的窗体 `Invoke`；
- 创建失败（非 Windows、后端不是 WinForms、pythonnet 异常）→ `attach()` 返回 False，
  `main.on_closing()` 就退化为「关闭即退出」，绝不因为托盘坏掉而卡住退出。

### 8.3 关窗 / 退出

## 9. 文件与数据格式

### 9.1 检查点 `文件名.ckpt.json`

路径：**按最终文件名**（`_probe()` 解析出 Content-Disposition 之后的
`cfg.output_path + ".ckpt.json"`），临时文件 `cfg.output_path + ".ckpt.tmp"`。

> 踩过的坑：`DownloadTask.__init__` 里就把路径算死，而文件名要等 probe 才知道 ——
> 结果是所有「没手填文件名」的任务都写到 `<保存目录>\download.ckpt.json`，重启后按
> 文件名根本找不到进度，同目录多个这类任务还会互相覆盖检查点。现在改成惰性属性
> `DownloadTask.ckpt`：`cfg.filename` 一变就跟着换路径。

```json
{
  "version": 2,
  "url": "https://dl-xxx.drive.quark.cn/...(签名直链，仅排障用)",
  "filename": "model.bin",
  "save_dir": "C:\\...\\下载",
  "total_size": 134217728,
  "chunk_size": 4194304,
  "chunk_span": 4194304,
  "completed": [0, 1, 2, 5, 8],
  "etag": "\"abc\"",
  "last_modified": "Wed, 22 Oct 2026 03:00:00 GMT",
  "user_agent": "Mozilla/5.0 ...",
  "referer": "https://pan.quark.cn/",
  "cookie": "__pus=...",
  "saved_at": 1761234567.891
}
```

| 字段 | 说明 |
|---|---|
| `version` | 格式版本，当前 2（v1 仍能读：没有 `filename` 时按下面的「旧检查点认领」处理） |
| `url` | **只用于排障，不再参与恢复判定**——签名直链几小时就换一条，拿它比对等于每次判脏 |
| `filename` / `save_dir` | 恢复身份：文件名必须与本次解析出的目标名一致 |
| `total_size` | 必须与本次探测一致 |
| `chunk_size` | 当前设置的分块尺寸（诊断用） |
| `chunk_span` | **实际生效**的分块跨度；恢复时优先沿用它重新切块，保证索引不错位 |
| `completed` | 已完成块索引（闭区间语义由 `chunks` 决定，索引越界会被过滤掉） |
| `etag` / `last_modified` | 服务器给就用来判定「还是不是同一个文件」；两边都有且不等 → 判脏 |
| `user_agent` / `referer` / `cookie` | 当时的凭据快照（排障用，恢复时仍以当前会话为准） |
| `saved_at` | 写入时间戳 |

写入策略（`checkpoint.py`）：**原子**——写 `.tmp` → `flush` → `fsync`（失败忽略）→ `os.replace`。
落盘时机：每完成一块（最多 1 秒一次，`_maybe_checkpoint`）、`_monitor` 每 3 秒、
暂停 / 出错 / 取消时（`run()` 的状态判定分支）；**正常完成时删除检查点**（`_finalize`）。

**断电安全水位线**（`_save_checkpoint(sync=...)`）：数据文件的 `fsync` 最多 5 秒做一次
（每次落盘都刷会在大文件上拖住事件循环），所以周期落盘只记录「确定已落盘」的
`completed` 快照，进度最多滞后 5 秒；暂停 / 出错 / 取消 / 完成这些**终态**落盘会
先刷数据、再记全量进度，一次都不丢。方向永远安全：宁可重下几秒，也绝不声称那些
其实还躺在系统缓存里的块已经写好了。

> 配套前提：Worker 的文件句柄是 `open(path, "r+b", buffering=0)` 打开的。若用默认缓冲，
> 每个句柄的用户态缓冲里最多会留 8KB，而 `_flush_data` 是**另开一个句柄**做 fsync ——
> 刷不到那些尾巴，"检查点不领先于磁盘"就成了空话。

**脏检查点自愈**（`_build_and_restore` + `_ckpt_verdict`）：文件名不一致 / ETag 或
Last-Modified 变了 / 总大小不一致 / 输出文件不存在 / 输出文件小于 `total_size` →
打印告警、从头下载；这样绝不会向服务器发出越界的 Range 请求。

> **必须清空 `self.completed`**（`_build_and_restore` 在判定前先 `self.completed = set()`）。
> 它可能还留着上一轮的索引（同进程暂停后重跑），或由 `_task_from_record` 从检查点预填。
> 判定失败却不清空的话，那些块会被当成「已完成」跳过，而文件刚被 `truncate` 成空洞 →
> 产出**大小正确、内容大片为零**的假完成文件（`_finalize` 只校验大小，看不出来）。
> 同理，任务索引恢复时若数据文件已不在/被截短，进度一律按 0 处理
> （`_data_file_ok`；已完成的任务会降回「已暂停」并提示重新下载）。

**旧检查点认领**（v1 没有 `filename` 字段，路径多半是 `download.ckpt.json`）：
只认「本地大小对得上 **且** 直链能佐证是同一个文件」——直链完全相同，或直链里的
文件名提示（夸克 `?filename=` / 路径末段）与本次目标名一致；认领成功后把旧文件改名到
正确位置。**认不准就不认**，而且判定不通过时**不删**旧文件（它可能属于同目录另一个任务）。

配合一个**最小 Range 服务器**即可测多线程/续传/限流：

```python
import asyncio

TOTAL = 48 * 1024 * 1024
DATA = b"x" * TOTAL

async def handle(reader, writer):
    head = await reader.readuntil(b"\r\n\r\n")
    hdrs = {}
    for line in head.decode("latin-1").split("\r\n")[1:]:
        if ":" in line:
            k, v = line.split(":", 1)
            hdrs[k.strip().lower()] = v.strip()
    rng = hdrs.get("range")
    if rng:
        a, b = rng.split("=", 1)[1].split("-")
        start, end = int(a), (int(b) if b else TOTAL - 1)
        end = min(end, TOTAL - 1)
        head_out = f"HTTP/1.1 206 Partial Content\r\nContent-Range: bytes {start}-{end}/{TOTAL}\r\n"
    else:
        start, end, head_out = 0, TOTAL - 1, "HTTP/1.1 200 OK\r\n"
    head_out += (f"Content-Length: {end - start + 1}\r\n"
                 "Content-Type: application/octet-stream\r\nConnection: close\r\n\r\n")
    writer.write(head_out.encode()); await writer.drain()
    pos = start
    while pos <= end:                     # 想模拟抖动：这里插入随机 sleep
        n = min(64 * 1024, end - pos + 1)
        writer.write(DATA[pos:pos + n]); pos += n
        await writer.drain()
    writer.close()

async def main():
    srv = await asyncio.start_server(handle, "127.0.0.1", 8000)
    async with srv: await srv.serve_forever()

asyncio.run(main())
```

要点：`_probe()` 靠 `Content-Range: bytes 0-1/总数` 取总大小，所以服务器**必须**返回
206 + 合法的 `Content-Range`；`Connection: close` 没问题（httpx 会自动重连）。

### 11.4 验证清单（改引擎后至少跑一遍）

| 项 | 判据 |
|---|---|
| 分块下载 | N 并发跑完，目标文件 SHA256 与源一致 |
| 暂停/继续 | 暂停后 `.ckpt.json` 存在且 `completed` 非空；继续后完成、哈希一致、检查点被删 |
| 脏检查点 | 改 `filename` / `total_size` / `etag` → 判脏、清空进度、从头下，不发越界 Range；**只换签名直链**（URL 变了但文件名 + 大小 + ETag 相同）必须接上进度 |
| 断电安全水位线 | 刚完成、还没到 flush 间隔的块不写进检查点；暂停/停止/出错/完成这些终态落盘必须先刷数据再写全量进度；Worker 句柄必须 `buffering=0`（否则 fsync 刷不到它的用户态尾巴） |
| 判脏清空进度 | 内存里已有 `completed` + 数据文件不存在 → `_build_and_restore` 必须清空 `completed` 与 `_durable_completed`；端到端「下到一半 → 删文件 → 继续」必须重新下完且 SHA256 一致（**曾经会产出全零的假完成文件**） |
| 任务索引 + 文件缺失 | 重启后数据文件已被删：进度按 0 显示、已完成的任务降回「已暂停」，点继续能重新下完 |

| 一次 429 不钉死自适应 | 探测中吃到一次 429：收敛到「实测档位」而不是被临时砍下来的值，`target` 不被压到 8 以下 |

| 并发热改 | 下载中把并发改成 3：`limiter.current` 立即为 3，在途分块跑完后 `active ≤ 3`，且自适应被关掉 |
| 并发自适应 | 服务端「并发越高越慢」时收敛到低档位并写 `adapt_note`，不一路爬到上限 |
| 任务索引 | 退出程序 → 重启 → 任务列表仍在（状态 paused、进度来自检查点）→ 点继续能下完且 SHA256 一致；已完成的卡片重启后仍是 100% |
| 同目录多任务 | 两个都没手填文件名的任务：各自写 `<各自文件名>.ckpt.json`，不出现共用的 `download.ckpt.json`，两个文件互不污染 |
| 一键回归 | `py -3.13 tests\test_resume_e2e.py`：本地 Range 服务器跑 15 组、70 项断言，不依赖外网；`py -3.13 tests\test_quark_fix.py`：夸克 UA / 票据刷新 / 不转存的离线断言；`py -3.13 tests\test_baidu.py`：百度 wxlist / 提取码 / sharedownload 字段 / dlink UA / 112·118 重试的离线断言 |
| 412 提示 | `cookie` 有/无两种配置下 `_auth_hint(412)` 文案正确、不抛异常 |
| 429 | 服务器返回 429 → 退避后继续，最终完成 |
| 速度 | 暂停/停止/完成时 `speed == 0` 且 `eta is None`（含 `pause_task` 返回的快照） |
| 偏好记忆 | 改目录 / 并发 / 分块后 `app_settings.json` 落盘；重启后 `get_settings()` 回填；空目录回落到默认 `下载/`；脏值被夹取（并发 1..256，分块 2..5MB） |
| 分享分类 | CDN 直链 → `direct`；`pan.quark.cn/s/…` → `share`；`pan.baidu.com/s/…` → `share`（百度解析器）；未接入网盘 → `unsupported_share` |
| 百度列目录（真机 / 离线） | 真机：`/s/1tPzn…?pwd=eh9y` 根目录 1 个文件夹 → `dir=/路径` 进入后 3 个文件；离线：shorturl 含 1、`root=1|0`、`mispwd-9` 区分缺码/错码、文件夹 key 用路径 |
| 百度直链（离线 mock） | `gettemplatevariable` → `tplconfig` → `sharedownload` 全链路字段正确；未登录 `9019` → `need_login`；`-20` 风控文案；`112` 刷新 sign；`118` 重取 seckey；dlink UA=`pan.baidu.com`；302 预解析成最终地址 |
| 目录下钻 / 批量 | mock：根目录翻页 100+20=120（含文件夹）；`list_dir` 子目录返回 3 项；16 个文件按 15+1 批量签发；批量提交创建 16 个任务；`list_share_dir` 往返正确 |
| 分享异常映射 | mock 响应：31001 → `need_login`；23018 → `need_login`（「被当访客 / 票据过期」，会弹登录窗）；缺提取码 → `passcode_required`；错码 → `passcode_wrong`；取消/失效 → `error` |
| 分享真机链路 | 真实分享链接：`resolve_link` 出文件列表 → `add_download` 建任务 → 直链落地（2026-11-07 用 248MB 文件实测：签发 `code=0`、`Range` 206；签不出来先按 4.7 查 UA 与 `__puus`） |
| 会话凭据可信 | 用会话 Cookie 直接打 `pan.quark.cn/account/info` 应返回昵称、`drive-pc.quark.cn/1/clouddrive/member` 应 `code=0`；返回 `31001 require login [guest]` 就是没带上会话 |
| 清空登录只清自己 | `clear_session("quark")` 后 baidu 的 Cookie 仍在（`_delete_site_cookies` 按域名删，不再 `DeleteAllCookies`） |
| 界面 | `pywebviewready` 后卡片渲染、`task_update` 推送生效、非传输状态显示 `—` |
| 退出 | 关窗/托盘退出后进程数回到基线，不留 `EBWebView` 孤儿进程 |

### 11.5 常见坑（都真实踩过）

| 现象 | 原因 / 对策 |
|---|---|
| `412` 打遍所有头组合 | 缺会话 Cookie；用内置会话，不要靠伪造指纹 |
| 带了 Cookie 仍 412 | 服务端按 TLS/JA3 拦客户端 → `_fallback_transport()` / `curl_cffi` |
| `Object of type Future is not JSON serializable` | API 层必须 `.result()` 后返回 |
| 首页误报「请通过 main.py 启动应用」 | `mounted()` 早于 `window.pywebview.api` 注入，等 `pywebviewready` |
| `GetCookiesAsync` 返回不该有的 Cookie | 自己按 RFC 6265 过滤（`filter_for_url`） |
| `AsyncSession(... connect_timeout=...)` TypeError | async 版没有这个参数，只传 `timeout` |
| `_CurlResponse` 没有 `aread` | 适配层要补齐引擎用到的全部方法 |
| 托盘图标残留在任务栏 | 退出时 `dispose()`/`dispose_direct()`；主窗 `FormClosed` 里必须直接销毁 |
| 关机后「文件在、续不上」 | 检查点路径在 `_probe()` 之前就被写死成 `download.ckpt.json`；对策是惰性 `DownloadTask.ckpt` + 旧检查点认领（见 9.1） |
| 换了直链就从头下 | `_ckpt_verdict` 曾要求签名直链逐字相同，而直链重新签发必然不同 → 每次都判脏；改成按文件名 + 大小 + ETag 认领 |
| 进度显示一跳一跳 | 分块跨度按 `total // concurrency` 取，分块数≈并发数，所以一批块几乎同时完成 |
| 托盘菜单点一下卡死 | 菜单回调在 UI 线程，不要在里面再 `Invoke` pywebview |
| 双击 .bat 开出两个实例 | 单实例互斥体只在 GUI 模式生效，确认 `_acquire_instance_mutex()` 被调用 |
| 前端速度显示「抖」或暂停后残留 | 见 3.8 的三重归零；非传输状态统一显示 `—` |
| 已登录却提示「未登录 / 请扫码」 | `_read_cookies` 改错对象：pywebview 6 里 `GetCookiesAsync` 用的是 **`EdgeChrome.url`**（`BrowserForm.browser.url`），`BrowserView.instances[uid]` 是 `BrowserForm`，改它的 `url` 无效。见 6.3 |
| 分享链接报「游客可下载大小受限」 | 服务端没把请求当已登录客户端：**Cookie 没带上 / `__puus` 过期 / 还在用浏览器 UA**。三条都查一遍；见 4.7 |
| 百度分享「链接出错了」（errno=2） | 用了已废弃的 `/share/list`；改用 `/share/wxlist`，且 `shorturl` 必须带开头 `1`（见 4.7） |
| 百度点文件夹报「不存在此目录」 | 文件夹 `ShareFile.key` 传成了 `fs_id`；wxlist 的 `dir` 要绝对路径，见 4.7 第 3 条 |
| 百度直链 403 / 下载 0 字节 | dlink 的 UA 不是 `pan.baidu.com`；检查 `ResolvedFile.user_agent` 是否被表单 UA 覆盖 |
| 百度签发回 9019 need verify | 会话没有 BDUSS（匿名只能列目录）或登录态过期；重新扫码后再解析 |
| 百度签发回 -20 | 触发风控验证码；在登录窗打开 `pan.baidu.com` 手动过一次验证，或等一段时间 |
| `clear_cookies()` 把别的网盘登录也清了 | pywebview 底层是 `DeleteAllCookies()`；按域名删要用 `_delete_site_cookies()`（UI 线程 + `GetCookiesAsync` + `DeleteCookie`） |
| `CoreWebView2 can only be accessed from the UI thread` | 所有 CookieManager 调用都要经 `form.Invoke(Func[Type](...))`，结果用信号量等 |
| `window.clear_cookies()` 报 `CoreWebView2` 线程错误 | 同上：切到 UI 线程 |

### 11.6 真机接口实测（判断是「凭据问题」还是「站点限制」）

网盘的 Cookie 是 App-Bound 加密的，**Python 侧解不开**，必须先让 WebView2 解密再拿出来。
标准做法是开一个隐藏窗口、用同一个 `storage_path` 启动，然后调 `session.capture()`：

```python
import os, threading, time, webview
from app.session import SessionManager

BASE = r"C:\path\to\any-downloader"      # 改成你自己的项目根目录
out = {}

def worker():
    time.sleep(3)                       # 等 webview.start() 起来
    cap = SessionManager().capture("https://pan.quark.cn/s/abcdef")
    out["logged_in"] = cap["logged_in"]
    cookie, ua = cap["cookie"], cap["user_agent"]
    # 用这组 Cookie 直接打接口，就能判断服务端认不认
    import httpx
    h = {"User-Agent": ua, "Referer": "https://pan.quark.cn/", "Cookie": cookie,
         "Content-Type": "application/json"}
    with httpx.Client(headers=h, timeout=20) as c:
        out["account"] = c.get("https://pan.quark.cn/account/info",
                               params={"fr": "pc", "platform": "pc"}).text[:120]
        out["member"] = c.get("https://drive-pc.quark.cn/1/clouddrive/member",
                               params={"pr": "ucpro", "fr": "pc"}).text[:120]
    for w in list(webview.windows):
        w.destroy()

threading.Thread(target=worker, daemon=True).start()
webview.create_window("probe", html="<html></html>", hidden=True)
webview.start(private_mode=False, storage_path=os.path.join(BASE, "会话数据"))
print(out)
```

判读口径（这几条都是实测过的）：

| 接口 | 认会话时 | 没认会话时 |
|---|---|---|
| `pan.quark.cn/account/info` | `data.nickname` 有值 | `data: {}` |
| `drive-pc.quark.cn/1/clouddrive/member` | `code=0`，含 `use_capacity / total_capacity` | `401` + `31001 require login [guest]` |
| `file/download`（自有文件） | `code=0` + `download_url` | — |
| `file/download`（分享文件） | `code=0` + `download_url` | `23018 download file size limit` |
| 签出的直链 `Range: bytes=0-1023` | `206` + `content-range` | `412`（`__puus` 过期）/ `403 RequestDeniedByCallback` |
| `sharepage/token` / `detail` | 不需要登录也能成功（游客可浏览分享） | — |

> 注意：
> - 测试时**不要**调 `api.clear_session()`（历史上它会把整个配置目录的 Cookie 清空）；
> - **分享签发必须用 PC 客户端 UA**（`API_UA` = `quark-cloud-drive/2.5.x`）。用 `navigator.userAgent`
>   那种浏览器 UA，超过访客上限的文件一律 `23018`（2026-11-07 同一组 Cookie 的 A/B 结果）；
> - `__puus` 会过期：列表接口仍正常，但直链下载 412 / 403。`session.capture()` 已经会先打
>   `auth/pc/flush` 换新票据；手工测试也应用 `refresh_cookie("quark", cookie)`；
> - 公开分享链接可以直接拿来测 `token/detail`（游客可读），不需要会话；
> - 项目里**没有转存代码**，也不要手工调 `sharepage/save`（会往用户网盘里存文件）。

## 12. 编码约定

1. **注释与文档字符串用中文**，解释「为什么这么做」，不要复述代码在做什么；
   踩坑点要写明白（本项目一半的注释是防回归用的）。
2. **类型注解必写**公开函数签名；`from __future__ import annotations` 放在文件首部。
3. **异常处理分层**：
   - 引擎内部：可恢复错误 → 重试/退避；不可恢复 → `_fail()` / `_FatalError`；
   - 事件推送、托盘、凭据刷新等「旁路」逻辑：**一律吞掉异常**，绝不能因为旁路失败中断下载；
   - UI 边界（`api.py`）：让异常抛出去，pywebview 会转成 rejected Promise，前端 toast。
4. **超时 / 阈值集中**在模块顶部的常量（`_COOKIE_TIMEOUT` / `_SPEED_WINDOW` / `_LOAD_TIMEOUT`
   之类），不要散落在函数里。
5. **不引入新依赖**除非功能必须；托盘、图标生成、cURL 解析都是刻意用标准库实现的。
6. **请求头只从 `build_headers()` 出**，不要在别处手拼——否则诊断结论会和真实下载不一致。
7. 前端保持「无构建」：不引入需要编译的语法（TS/JSX/SFC），不加 npm 步骤。
8. 改行为时同步三处：**代码注释**、**README（用户视角）**、**本文档（开发视角）**。

## 13. 已知限制与技术债

| 项 | 现状 | 影响 |
|---|---|---|
| 会话依赖 GUI | `webview.guilib is None` 时 `capture()` 直接返回空凭据 | CLI 只能用 `--cookie`；`resolve_link` / 分享任务也只在 GUI 下可用 |
| 按 host 复用探测窗 | `_probes[host]` 永不回收（直到进程退出） | 诊断过的域名多了会多几个隐藏窗 |
| 任务索引含明文凭据 | `tasks_state.json` 与 `*.ckpt.json` 都落了 Cookie / 直链 | 与既有检查点同级敏感度：这两个文件不要外传、不要随项目打包分发 |
| 纯直链任务过期需人工 | 分享任务续传会自动重签直链（`share_ref` + `_reissue_share_url`）；**直接粘贴的**签名直链失效后没有重签凭据 | 需要用户再取一条直链；**进度不会丢**（按文件名 + 总大小 + ETag 认领，换签名也能接上） |
| 分块数≈并发数 | 分块跨度按 `total // concurrency` 自适应，导致"一波并发块同时完成" | 界面进度是一跳一跳的（不是线性爬）；这是既有设计，改起来要动分块策略 |
| 单目录文件上限 | 夸克 detail 每页 100、最多翻 10 页（1000）；百度 wxlist 每页 1000、最多翻 20 页（2 万） | 超出上限时只列前面部分并在面板提示；文件夹不支持整包一键下载，需进入后勾选文件 |
| 百度直链需登录 | 匿名只能列目录；签发走 BDUSS 会话，未登录回 `9019 need verify` | 首次使用需在内置登录窗扫码一次；登录态过期要重扫 |
| 百度直链真机未复验 | 列目录 / 提取码 / sign 已真机验证；`sharedownload` 因本机无 BDUSS 仅做了离线 mock（54 项） | 拿到真实登录会话后按 4.7 末尾步骤复验一次 `list[0].dlink` + `Range 206` |
| 百度账号级限速 | 非 SVIP 是**账号级**限速，不是单连接限速 | 64 并发对百度不会叠加提速；这是百度策略，不是引擎问题，README 已写明 |
| 夸克接口字段未真机验证 | `detail` 列表层级、`download` 响应字段名来自公开源码比对；`token/detail/download` 已用真实分享链接实测通过（2026-11-07 含 248MB 文件） | 真实响应结构再变时报错，按 4.7 末尾说明只改 `quark.py` 映射 |
| 分享签发依赖客户端 UA | `_client()` 固定用 `API_UA`（PC 客户端）；用浏览器 UA 会被套上访客大小限制（23018） | 站点若再调整 UA 规则，表现为大文件签不出；改 4.7 的 UA 常量即可 |
| `__puus` 短时效 | 票据过期后列表正常、直链 412/403；靠 `app/cookie_refresh.py` 在取 Cookie / 签发前用 `__pus` 换新 | 刷新失败会退回原 Cookie（下载可能 412），不会阻断流程；`__pus` 本身过期只能重新扫码 |
| 23018 = 没被认成已登录客户端 | 两个来源：Cookie/票据失效、或用了浏览器 UA（见 4.7 实测） | 现在抛 `LoginRequiredError` 自动开登录窗；别再加「转存」兜底 |
| 无分块哈希 | 只校验整文件大小，不校验每块 | 断电场景已用「落盘水位线」降低风险（检查点永不领先于磁盘），文件被外部改写仍发现不了 |
| 缺 ETag 时身份变弱 | 服务器不给 `ETag`/`Last-Modified` 时，判据退化成「文件名 + 总大小」 | 同目录若有**同名同大小**的另一个文件，理论上会被认领；有 ETag 的站点不受影响 |
| CLI 与 GUI 的任务索引 | CLI 用 `DownloadManager(persist_tasks=False)`，不读也不写 `tasks_state.json` | 两边同时跑不会互相覆盖索引；代价是 CLI 的任务不出现在 GUI 列表里 |
| curl 后端句柄数 | `curl_pool_size()` 显式传 `max_clients`（默认 10 会把并发压到 10） | 已修；但 curl 后端的连接复用/限速行为仍与 httpx 不同 |
| 单任务独占并发 | 64 Worker 是**每任务**的 | 多任务同时跑会成倍抢带宽（路线图：全局连接预算） |
| 托盘仅 Windows | 非 Windows 退化为关闭即退出 | 可接受 |
| `_probe_window` 的 URL 固定 `/robots.txt` | 极少数站点把 robots.txt 重定向到别处会导致探测报「未能停留在该站点」 | 会退化为 `ERR`，不影响下载 |
